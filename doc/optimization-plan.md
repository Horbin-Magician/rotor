# Rotor 3.x 优化计划

本计划以当前工作区的 Rotor 3.0.2 为起点。目标是先获得真实负载的证据，再按用户可感知的收益选择实现工作，并为当前产品身份补齐原生验收。历史测量只作为对照，不作为当前版本的通过证明。

## 0. 范围与执行顺序

1. **先建立基线（P0）**：测出搜索、截图与内存的端到端表现，记录环境和波动范围。
2. **并行补当前版本验收（P0）**：执行 Windows 和 macOS 的实际安装、运行与失败恢复检查；更新验收记录。
3. **按基线选择性能改动（P1）**：优先处理用户等待时间或内存峰值最高的路径。macOS 索引冷启动和截图保存期间的像素副本是已知候选，不预设它们一定是最大瓶颈。
4. **把稳定、可重复的检查接入 CI（P2）**：真实设备、签名和人工交互检查继续保留独立验收记录。

所有测量使用独立合成资料目录，不读取真实用户资料、凭据或截图。开发与生产身份分开记录；不触碰已有用户资料目录。保留请求标识、取消与过期结果拒绝、配置/记录未知字段、原子写入顺序和更新失败恢复。

## 1. 建立端到端性能基线（P0，预计 2–4 人日）

### 1.1 定义场景和口径

| 场景 | 起点与终点 | 必须同时记录 |
| --- | --- | --- |
| 冷启动搜索 | 进程创建 → 搜索界面可用、首批结果可见 | 索引状态、文件数、索引大小、磁盘类型、CPU、私有内存峰值 |
| 暖启动搜索 | 快捷键触发 → 首批结果绘制 | 查询类型、索引是否已加载、图标出现时间、P50/P95 |
| 截图 | 快捷键触发 → 遮罩首帧呈现；确认选区 → 贴图可交互 | 每阶段耗时、显示器分辨率/缩放、CPU 与私有内存峰值 |
| 连续操作 | 连续截图、保存、OCR、关闭贴图 | 峰值内存、返回空闲后的内存、错误与取消次数 |

至少覆盖 Windows 与 macOS 各一台实机；每个平台记录单屏和双屏/混合缩放配置。合成搜索树分别使用小、中、大三档规模，明确文件数、目录深度和排除规则。冷启动与暖启动分开测；同一场景重复至少 30 次，记录 P50/P95、最差值和失败数，不把 OS 文件缓存命中当成真正冷盘结果。

### 1.2 补测量工具

- 复用 `ROTOR_CAPTURE_TIMING=1` 的阶段日志和 `capture_pipeline_bench`，增加可解析的测量汇总脚本。日志已经记录 `capture_requested`、`images_prepared` 和 `mask_show_requested` 等阶段，但最后一个只表示发出显示请求。
- 在 Windows/macOS 原生窗口层补“首帧已提交/窗口已显示”的观测点，并标明它是应用侧呈现时间；需要验证实际屏幕可见时间时，另用外部录像或人工观察，不把隐藏窗口预绘制当成可见首帧。
- 为搜索增加同一请求标识下的“索引可用、查询提交、首批结果发布、首批绘制”时间点。记录查询文本长度或类别即可，不写入真实查询内容。
- 扩展现有空闲资源测量方案，增加**索引开启、快捷键开启、交互负载**的独立场景。原 `measure-windows-idle.ps1` 的结果仍只代表无索引、无快捷键的后台进程。
- 以机器、系统版本、构建身份、二进制哈希、显示配置、索引规模、测量命令和原始样本生成一份可复查报告。任何优化前后比较使用同一机器和场景，并交替运行顺序。

**完成条件**：两平台的场景定义与原始样本可复现；报告能把等待时间拆到索引、原生采集、像素准备和窗口呈现等阶段；明确指出高波动或无法测出的指标。此阶段不以合成 CPU 基准代替用户可见延迟。

## 2. macOS 搜索冷启动（P1，测量后决定；预计 4–8 人日）

**现状**：可移植索引没有覆盖进程离线期间变化的持久事件游标，启动时调用 `WalkDir` 全量扫描。先用第 1 阶段数据确认全量扫描在目标规模下是否影响搜索可用时间。

1. **拆分耗时**：分别测目录遍历、索引构建、快照写入/读取、首个查询和图标加载；记录被排除目录、受保护目录、符号链接、APFS 卷与外置卷的行为。
2. **选择方案**：若遍历是主要瓶颈，评估 macOS 原生持久事件进度与快照组合。启动时先校验卷身份、事件历史连续性和快照格式，再重放变化；无法证明连续性时全量扫描。若原生游标方案代价过高，优先实现能保持结果正确性的分阶段索引与明确的“索引中”状态。
3. **保留正确性**：覆盖应用关闭期间的新增、删除、重命名、目录移动、排除规则变化、权限变化、事件溢出及卷重新挂载。任何缺失事件或损坏快照必须触发重建，不能静默返回过时结果。
4. **验证**：合成目录树的离线变更回归测试、macOS 实机重启测试、取消/重复查询/分页测试；按相同规模比较冷启动可搜索时间、CPU、磁盘读取和索引大小。

**候选目标**：在目标大目录场景下降低冷启动 P95，且搜索结果正确性、内存峰值与空闲资源不退化。具体量化门槛在第 1 阶段报告后固定，不事后调低门槛。

## 3. 截图与贴图的瞬时内存（P1，测量后决定；预计 3–6 人日）

**现状**：已完成的单缓冲准备优化降低了贴图长期持有的 CPU 像素；新截图保存期间仍可能同时持有显示和持久化缓冲区。先确认峰值出现在哪个阶段，区分 CPU 私有内存、工作集和 GPU 占用。

1. 用 1080p、4K、双 4K 场景测单次截图和连续十次“截图→标注/裁剪→保存/OCR→关闭”；记录每个活跃贴图的像素字节、编码队列长度和返回空闲后的内存。
2. 若峰值来自像素副本，评估只读共享像素视图、裁剪范围编码或缩短持久化输入生命周期。一次只改一条路径，避免同时改变显示、导出和存盘语义。
3. 逐项验证直通 alpha、隐藏 RGB、裁剪几何、PNG 字节、OCR 输入、保存失败后的贴图可用性、已接受写入顺序以及取消/过期结果拒绝。
4. 对照第 1 阶段同机样本，报告峰值私有内存、P95 首帧时间、P95 保存时间和失败数。若收益小于测量噪声，保留现有实现，不为理论字节数增加复杂度。

**完成条件**：确认峰值来源并给出优化前后报告；实现方案须在真实多屏交互中减少可观测峰值，同时不降低截图响应或存盘可靠性。没有显著收益时，以测量结论关闭此项。

## 4. 当前身份与版本的原生验收（P0，可与第 1 阶段并行；预计 3–5 人日，另需实机和发布凭据）

1. **更新证据**：新建 3.0.2 的验收记录，写明提交、二进制哈希、版本、开发/生产身份、系统与硬件。`doc/validation-status.md` 中的 3.0.0 旧身份结果保留为历史档案，不挪作当前通过记录。
2. **自动化门槛**：执行 `cargo fmt --all -- --check`、`cargo check --workspace --locked`、`cargo test --workspace --locked`、严格 Clippy、核心依赖检查、OCR smoke 和合成资料往返检查。按 `xtask build → stage → verify → package` 的顺序分别验证开发和生产身份，使用全新目标目录。
3. **Windows 安装**：在已提升权限的 PowerShell 7 会话中，用新的开发包和全新 `target` 子目录运行 `test-windows-install.ps1`，按条件启用恢复与空闲测量。生产安装/UAC、真实登录启动、快捷键、IME、多屏缩放、截图/OCR、翻译取消和托盘行为单列人工检查；开发身份脚本不证明生产路径。
4. **macOS 实机**：验证 `.app`/DMG 的身份、权限请求、屏幕采集、窗口呈现、搜索索引、快捷键、更新失败恢复。需要发布级结论时，再用真实签名/公证凭据完成 Gatekeeper 验收；便携单元测试不替代这一步。
5. **CI 补强**：评估把 `capture_paint_smoke` 加入可运行原生 GUI 的 Windows/macOS 测试环境。先验证隐藏窗口测试在 runner 上稳定，再作为门槛；真实多屏和安装矩阵保留人工/专用设备验收。

**完成条件**：当前版本和身份的自动化、安装及实机结果分别有证据；未执行的项明确标为未验证。发布判断只能引用当前构建的证据。

## 5. 每项改动的统一交付与回归要求

- 每项性能改动附问题场景、原始样本、优化前后统计、系统/硬件和二进制哈希；报告同时列出失败数与局限。
- 先运行受影响 crate 的测试，再运行工作区格式、编译、测试、Clippy 与依赖边界检查。截图变更额外运行 OCR smoke 和合成资料往返；搜索变更额外运行索引/分页/取消回归与对应的合成负载测量。
- Windows 结果不能推断 macOS 行为；隐藏窗口和合成资料测试不能推断真实屏幕、权限或安装结果。
- 完成第 1 阶段后按“用户等待时间 × 受影响频率 × 实现风险”排序第 2、3 阶段，并在开始改代码前固定目标场景与验收门槛。
